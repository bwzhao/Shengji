# 升级·找朋友 设计文档

版本 0.2 · 2026-09-10 · 规则细节已确认

## 1. 目标与范围

- 5 人或 6 人联机的「升级找朋友」，三副牌，熟人局。
- 网页游戏，做成 PWA，牌桌只按横屏设计，手机横过来玩，电脑直接可用。以后如需上架用 Capacitor 套壳。
- 第一版包含：房间码加入、完整规则引擎、断线重连、局间自动接庄。不做账号、匹配、排行。
- 服务端为唯一权威，客户端只渲染和发送操作。玩家在纽约，服务端部署在 Fly.io 纽瓦克（ewr）。

## 2. 规则形式化

### 2.1 牌与人数

| 项目 | 5 人 | 6 人 |
|---|---|---|
| 牌数 | 3 副 × 54 = 162 | 162 |
| 每人手牌 | 31 | 26 |
| 底牌 | 7 | 6 |
| 朋友数 | 1 | 2 |
| 总分 | 300 | 300 |

每张牌有唯一 id：`{deck: 0|1|2, suit: S|H|D|C|J, rank}`，王牌 suit 为 J，rank 为 `BJ`（大王）或 `SJ`（小王）。

### 2.2 等级与级牌

- 每位玩家各自记录等级。等级顺序不是自然点数序，而是：

```
5 → 10 → K → 2 → 3 → 4 → 6 → 7 → 8 → 9 → J → Q → A
```

- 所有人从 5 开始。升 k 级就是在这个序列上前进 k 步，到 A 为止不再前进。
- 当局级牌 = 庄家当前等级。首局无庄家，谁最终抢到主谁坐庄：先亮者暂为庄家，被反主则庄家换成反主的人，级牌为 5。非首局庄家已定，反主只改主花色。
- 庄家阵营打 A 且守庄成功，该阵营获胜，游戏结束。

### 2.3 发牌与亮主

- 出牌与发牌都按逆时针进行。从庄家的下家开始一张一张发，发完手牌为止，剩余为底牌。首局从房主开始发。
- 发牌过程中任何人可以亮主或反主。发完后再给 5 秒缓冲期，缓冲结束进入扣底。
- 亮主的高低只看张数：三张 > 两张 > 一张。反主必须比当前有效亮主多至少一张；张数相同不能反，先亮者有效。亮主者本人可以用更多张数加固，但不能改亮别的花色或改亮王。
- 可以亮的组合：

| 亮出的牌 | 结果 |
|---|---|
| 1 / 2 / 3 张同花色级牌 | 该花色为主 |
| 2 / 3 张小王 | 无主 |
| 2 / 3 张大王 | 无主 |
| 任意 3 张王，大小可混 | 无主 |

- 单张王不能亮，两张王必须相同；三张王不论大小混不混都可以亮。两张级牌、两张小王、两张大王互相之间不能反，因为张数相同。

- 无人亮主：非首局时翻底牌，第一张有花色的牌决定主花色，全是王则无主；首局重新发牌。
- 亮出的牌留在手中，只是公开。

### 2.4 扣底

庄家收进全部底牌，再扣回同样数量，任意牌都可以扣。扣底期间其他人只看到「庄家正在扣底」。

### 2.5 叫朋友

- 扣底后庄家宣布朋友牌：「第 n 张打出的 X」，n ∈ {1, 2, 3}。
- X 必须是副牌：不能是主花色、不能是级牌、不能是王。
- 5 人叫 1 个，6 人叫 2 个。两个可以指向同一张牌的不同序号，例如「第一张 ♠A」和「第二张 ♠A」。
- 序号按所有人打出的 X 累计，庄家自己打出的也算。庄家自己打出第 n 张时，该朋友位由庄家占据，等于空缺。
- 谁打出第 n 张 X，立刻公开成为庄家阵营。若 6 人局两张朋友牌由同一人打出，庄家只有一个朋友。
- 若朋友牌被扣在底牌而从未打出，该朋友位空缺。
- 所有朋友位揭晓（或确定不可能揭晓）之前，其余玩家都是「未知」身份；引擎在每墩结束后判断是否已可确定闲家阵营。

### 2.6 牌力顺序

主花色为 T，级牌为 R：

```
大王 > 小王 > T·R（主级牌）> 其他三色 R（副级牌，三者相等）> T·A > T·K > … > T·2（跳过 R）
```

无主时：`大王 > 小王 > 四色 R（相等）`，不再有其他主牌。

主牌集合 = 王 + 所有级牌 + T 花色牌。副牌花色内部：A > K > … > 2，跳过 R。

### 2.7 牌型

同一花色（主牌视为一个花色）内：

| 牌型 | 定义 |
|---|---|
| 单张 | 1 张 |
| 对子 | 2 张同花色同点数 |
| 三条 | 3 张同花色同点数 |
| 拖拉机 | 点数连续的 k 个对子或 k 个三条，k ≥ 2，同花色 |
| 甩牌 | 同花色多个牌型的组合，首出时每个组件都必须大过其他所有人手中同花色的对应牌型 |

拖拉机的连续性用「序位」判定：主牌内 …K, A, 副级牌, 主级牌, 小王, 大王 各占一个序位，三个花色的副级牌共享同一序位，因此两个不同花色的副级牌对子不构成拖拉机，但主 A 对 + 主级牌对可以。三条和相邻对子不混合成拖拉机。副牌内的序位按 A > K > … > 2 跳过级牌，因此级牌为 5 时，副牌 6 对 + 4 对是拖拉机。

甩牌失败：强制打出其中最小的组件，并按甩牌的总张数每张罚 10 分给对方阵营。庄家阵营甩牌失败，罚分直接加到闲家得分上；闲家甩牌失败，从闲家得分中扣除，最低扣到 0。

### 2.8 跟牌与赢墩

首出 n 张、花色 s、结构 S。跟牌者按顺序满足：

1. 有 s 花色必须出 s 花色，不够 n 张则全部出完再用其他牌补足。
2. 结构匹配优先：首出含三条则有三条必须出三条；含对子则有纯对子必须出对子，三条不必拆开去跟对子或对子拖拉机，但自愿拆开出是合法的；含拖拉机则有同长拖拉机必须出，否则尽量出对子。
3. 无 s 花色：任意出 n 张。若全部是主牌且结构与 S 匹配，则参与毙牌比较。

赢墩：首出花色内结构匹配且最大者，或主牌结构匹配且最大者；主牌毙牌胜过副牌。甩牌被毙时，毙牌方必须用主牌覆盖甩牌的全部结构，比较以甩牌中最高等级的组件为准（拖拉机 > 三条 > 对子 > 单张，同类型比最大牌）。

赢墩者收走本墩所有分牌，并首出下一墩。

### 2.9 计分

- 5 = 5 分，10 = 10 分，K = 10 分，每副牌 100 分，总 300 分。
- 抠底：闲家赢最后一墩时，底牌中的分按最后一墩的牌型翻倍，与张数无关：单张 ×2，对子 ×4，拖拉机 ×8。三条按 ×8 处理，见待确认清单。
- 闲家得分 P = 抓分 + 抠底 + 甩牌罚分。5 人和 6 人的阶梯不同：

| 5 人（60 分一级） | 6 人（50 分一级） | 结果 |
|---|---|---|
| 0 | 0 | 大光，庄家阵营升 3 |
| 5 ~ 59 | 5 ~ 49 | 庄家阵营升 2 |
| 60 ~ 119 | 50 ~ 99 | 庄家阵营升 1 |
| 120 ~ 179 | 100 ~ 149 | 下庄，闲家阵营不升 |
| 180 ~ 239 | 150 ~ 199 | 下庄，闲家阵营升 1 |
| 240 ~ 299 | 200 ~ 249 | 下庄，闲家阵营升 2 |
| 300 | 250 ~ 299 | 下庄，闲家阵营升 3 |
| – | 300 | 下庄，闲家阵营升 4 |

- 用公式表达：设一级为 L（5 人 60，6 人 50），下庄线为 2L。P = 0 时庄家阵营升 3（大光）；0 < P < 2L 时庄家阵营升 `2 - floor(P / L)`；P ≥ 2L 时下庄，闲家阵营升 `floor(P / L) - 2`。四人模式同样适用。
- 升级只作用于获胜阵营的全体成员，各自沿 2.2 的等级序列前进，到 A 为止。

### 2.10 下一局庄家

从当前庄家沿出牌方向（逆时针）数，第一个属于获胜阵营的玩家接庄：

- 守庄成功：第一个庄家阵营成员，即最近的朋友。若本局没有朋友现身，庄家连庄。五人局例外：守住就由原庄家连庄（第 7 节第 16 条）。
- 下庄：第一个闲家。

座位顺序在整局游戏中固定，房主开局前可拖动调整。

### 2.11 四人对家模式

房主开房时可选「4 人 · 对家一队」，是经典四人升级，不找朋友：

| 项目 | 取值 |
|---|---|
| 牌数 | 2 副 × 54 = 108 |
| 每人手牌 | 25 |
| 底牌 | 8 |
| 总分 | 200 |
| 计分 | 40 分一级，80 分下庄（公式同 2.9，L = 40） |
| 等级 | 从 2 开始、A 结束（2 → 3 → … → K → A）；第一次到 5、10、K 不能跳过，例如打 4 升两级只能到 5 |
| 获胜 | 在 A 上坐庄并守住才算赢下整局；闲家升到 A 为止，还要上庄再守住 |
| 队伍 | 对家固定一队，两人共用等级 |
| 接庄 | 守庄换对家坐庄，下庄换庄家的下家 |

亮主阶梯与找朋友不同：一张级牌 < 一对级牌 < 一对小王 < 一对大王，一对王可以盖一对级牌，一对大王可以盖一对小王，不能用三张牌亮主。甩牌罚分、抠底倍数、首局抢庄规则与找朋友一致，等级阶梯见上表。扣完底直接开打，没有叫朋友阶段，身份从开局就全部公开。机器人在这个模式下不做垫门找朋友，扣底按普通打分，配合规则全部生效。

## 3. 系统架构

```
shengji/
├─ package.json            pnpm workspaces
├─ packages/engine/        纯规则引擎，零运行时依赖，前后端共用
├─ packages/protocol/      zod 定义的消息 schema 与 PlayerView 类型
├─ apps/server/            Node 22 + ws + Fastify，权威状态
├─ apps/web/               React 19 + Vite + vite-plugin-pwa
└─ docs/DESIGN.md
```

全部 TypeScript，严格模式。引擎不引用任何 Node 或浏览器 API，可以在服务端、浏览器和测试里跑同一份代码。

### 3.1 引擎

```ts
createGame(config: GameConfig, seed: string): GameState
applyAction(state: GameState, action: Action): { ok: true, state, events } | { ok: false, error }
viewFor(state: GameState, seat: Seat): PlayerView
validateFollow / validateLead                 // 客户端选牌时的即时校验
generateFollow                                // 机器人与「提示」按钮共用
```

- 纯函数、不可变数据。洗牌用带种子的 xoshiro128，同一 seed 加同一操作序列可以完整复现一局，操作日志就是回放文件。
- `Action` 包括 `declare`、`exchangeBottom`、`callFriend`、`play`，以及服务端定时触发的 `dealCard` 和 `closeDeclaring`。
- `RuleError` 带机器可读 code 和面向玩家的中文说明，例如 `MUST_FOLLOW_SUIT: 手里还有黑桃，必须先出黑桃`。
- `PlayerView` 只包含该座位可见的信息：自己的手牌、已公开的亮主牌、当前墩、历史墩的分牌、已揭晓的身份。底牌只对庄家可见。
- 客户端用 `validateFollow` 和 `validateLead` 做选牌时的即时校验，用 `generateFollow` 实现「提示」。

### 3.2 状态机

```
lobby ─start─▶ dealing ─(发完)─▶ declaring(5s) ─▶ bottom ─▶ callFriend ─▶ playing ─(31/26 墩)─▶ roundEnd
                 ▲                                                                                │
                 └──────────────────── 下一局，接庄 ◀─────────────── 未分胜负 ◀───────────────┘
                                                                        │ 庄家阵营守住 A
                                                                        ▼
                                                                    gameOver
```

`dealing` 和 `declaring` 阶段都接受 `declare`。`playing` 内部由 `trick` 子状态记录当前首出、已跟牌者和待出牌者。

### 3.3 服务端

- 一个 Node 进程，内存中的 `Map<roomCode, Room>`。房间码 4 个字母，去掉 I、O、L 等易混字符。
- 每个房间持有 `GameState`、操作日志、各座位的连接和会话 token。
- 发牌用定时器逐张推送 `cardDealt` 事件，间隔 150 毫秒（六人一轮发完约 23 秒），发完再留 5 秒亮主缓冲。
- 断线：座位保留，期间该玩家的回合暂停等待，其他人看到离线标记。玩家主动离开房间时该座位由机器人接管。开局前房主可以往空位添加机器人，方便人数不够时测试。
- 机器人以二十位电影明星命名（十位男演员、十位女演员），同一房间不重名；头像照片放在仓库 `apps/web/public/avatars`，全部取自 Wikimedia Commons 的自由授权或公有领域图片，同目录 `CREDITS.md` 逐张列出作者与授权；真人玩家显示名字首字的色块。
- 每次变化后一秒内把所有房间与会话写成 `rooms.json` 快照（原子替换），启动时读回并重新挂上定时器，进程重启不丢局。空闲 2 小时的房间回收。
- 每 30 秒对所有连接 ping，一轮没有 pong 的连接直接断开，避免手机切后台后留下僵尸连接。
- 房间里没有任何真人在线时，发牌、亮主缓冲、机器人出牌和自动下一局全部暂停，不空转；任何一位真人连回来立刻继续。断线玩家的座位一直保留，直到房间在最后一次真人操作 2 小时后被回收。
- 回合计时默认关闭，房主可开 30 秒，超时自动出合法最小牌。

### 3.4 网络协议

WebSocket，JSON 文本帧，路径 `/ws`。所有消息带 `t` 字段。

客户端 → 服务端：

| t | 载荷 | 说明 |
|---|---|---|
| hello | name, token? | 建立或恢复会话，token 存在 localStorage |
| createRoom | config | 返回 roomCode，创建者为房主 |
| listRooms | – | 首页列出服务器上现有的房间：人数、进度、房主、在座的人、是否可进、能否关闭 |
| closeRoom | code? | 关闭房间并删除牌局，成员全部回首页。房主可关任何状态的房间，没有真人在线的房间任何人可关 |
| joinRoom | roomCode | 进入大厅；房间已开局时接管一个机器人座位 |
| sit / stand | seat | 选座、离座 |
| leaveRoom | – | 离开房间；游戏中退出则座位由机器人接管，房主顺延给下一位真人 |
| reorder | seats[] | 房主调整座次 |
| start | – | 房主开局 |
| setBots | strength | 房主设置机器人强度：normal 规则机器人，strong 搜索机器人 |
| declare | cardIds[] | 亮主或反主 |
| exchangeBottom | cardIds[] | 扣底 |
| callFriend | calls[] | `{suit, rank, nth}` |
| play | cardIds[] | 出牌 |
| addBot / removeBot | seat | 房主往空位添加或移除机器人 |
| restartRound | – | 房主重发本局：等级、局数、庄家保留，当前进度作废 |
| abortGame | – | 房主结束游戏回大厅：座位与机器人保留，等级归零 |
| getReplay | round | 请求某一局的回放 |
| ping | – | 保活 |

服务端 → 客户端：

| t | 载荷 | 说明 |
|---|---|---|
| welcome | token, name | 会话建立 |
| room | room 或 null | 大厅信息：座位、房主、是否已开局 |
| state | seq, view, events | 该座位的完整视图加本次变化的事件 |
| error | code, message | 引擎的 RuleError 直接透传 |

事件 `e` 的类型：`playerJoined`、`playerLeft`、`seated`、`cardDealt`、`declared`、`declaringClosed`、`bottomTaken`、`bottomExchanged`、`friendCalled`、`cardsPlayed`、`friendRevealed`、`trickWon`、`roundScored`、`dealerChanged`、`gameOver`、`playerDisconnected`、`playerReconnected`。

第二阶段的实现每次变化都下发完整视图而不是增量事件，视图很小（几十张牌），简单可靠；`events` 只用于客户端做提示与动画。重连时用 localStorage 里的 token 重新 `hello`，服务端识别后补发 `room` 和 `state`。所有客户端消息用 zod schema 校验，schema 放在 `packages/protocol` 供两端引用。发给某座位的 `cardDealt` 事件里，别人的牌会被抹掉。

### 3.5 前端

- 手机竖屏优先。上方是其他玩家的弧形座位，每人显示昵称、等级、身份标记：庄家金色，已揭晓朋友金边，未知灰色，确定的闲家蓝色。
- 中央是当前墩，赢墩后飞向赢家。每人出的牌落在固定的出牌位：顶上一排在各自座位正下方，两侧的牌放在座位内侧，五六人时两侧再往下放、避开顶上一排；每个出牌位有最大宽度（牌桌宽度的 19% 到 26%）。牌多时先缩小牌间距（最少露出 14 像素），还放不下再整排缩小；牌桌被上方信息行压矮时也按比例缩小。桌上有牌时，中间的提示文字挪到左上角。
- 这一墩目前谁最大实时标出：那一手加金框，随每张出牌移动；用的是和服务端同一个 trickWinner 计算。上一墩收走和查看上一轮时标的是赢家。
- 操作区里「上一轮」和「提示」并排在「出牌」上方（出牌阶段显示，打完第一墩前是灰的）：点一下把上一墩每人出的牌摆回各自的出牌位，赢家那手加金框，左上角提示改成「上一轮：某某赢，多少分」，座位牌上的「首」移到上一墩先出牌的人；3 秒后自动收起，或再点一下「收起」。新的一墩结束时自动收起，因为那时「上一轮」已经换了一墩。
- 出牌布局校验：在 667×375、844×390、932×430、1024×768、1440×900 五种尺寸下，四五六人每个座位同时出 1 到 12 张牌，用脚本量出牌之间、出牌与座位牌、出牌与提示之间的重叠。四人、五人全部不重叠；六人只在最小的 667×375 上出 10 张以上时有 1 到 3 像素的边角相碰。
- 底部是手牌扇，横向可滚动，从大到小、从左到右排：主牌在最左（大王打头），副牌按花色红黑交错、每门从 A 到 2；桌上出的牌、回放和结算面板里的底牌也按同样的顺序，新发到的牌有滑入动画。点击抬起选中，再点「出牌」。跟牌时手里有该花色则其他花色变暗；选满张数后用引擎的 `validateFollow` 即时校验，不合法时「出牌」禁用并显示原因；「提示」用 `generateFollow` 给出一个合法出法。
- 顶栏常驻：房间码、局数、级牌、主花色、闲家当前得分、底牌数。找朋友模式里，朋友未全部现身时身份未定者抓的分不计入闲家分，单独显示为「待定」；顶栏下一行列出朋友牌和闲家抓到的分牌，两样合成一行，免得把牌桌压得太矮。分牌不画牌面，只写花色、点数和张数，例如「♠K×2 ♥10 ♣5×3」，按花色顺序和 K、10、5 排列；身份未定者抓的分牌另列在「待定」后面，颜色变暗。已确认的闲家收到带分的墩时播放掌声。
- 发牌阶段手牌逐张飞入，能亮主时按钮亮起并列出可用的亮主组合。
- 回合结束弹结算面板：每墩分、抠底倍数、各人升级、下一局庄家。底部按钮钉在面板底边，手机横屏不用往下滚就能看到：每局结束是「回放本局、退出本局、下一局」（下一局只有房主能点）；整场游戏结束是「回放本局、退出、回到大厅」，房主点「回到大厅」后座位保留、等级归零，可以直接再开一局。
- 电脑横屏把座位改成环形，手牌单行铺开。
- PWA：vite-plugin-pwa 生成 manifest 与 service worker，静态资源预缓存，WebSocket 不经过 service worker；图标由 `apps/web/scripts/icons.mjs` 用纯 Node 画出 PNG。
- 音效：出牌、轮到你、收墩、朋友现身、错误用 Web Audio 合成；掌声与亮主的狗叫用 Wikimedia Commons 的公有领域与 CC BY-SA 录音，裁剪后放在 `public/sounds`（授权见同目录 `CREDITS.md`），首次触摸后预取解码，加载失败退回合成音。顶栏可静音。

### 3.6 机器人策略

`packages/engine/src/smartbot.ts`，不做搜索，只用牌桌常识，同一套代码在服务端补位和模拟器里运行。四个特性可以单独开关，便于用模拟器做 A/B 对比：

- **记牌**：用已出的牌、自己的手牌和（庄家可见的）底牌算出每个身份还剩几张在外面，据此判断一个牌型是否已经压不住；同时记录谁在哪个花色已经断门。
- **亮主（declare）**：对每个可亮的花色算「牌力」：按发牌进度外推最终主牌张数，加上大小王、级牌、主 A/K 的高牌分、主牌里的对子数和副牌缺门数。单张级牌要 11.5 分才亮，对子 9.5 分，三张必亮；发牌不到一半时更谨慎，快发完还没人亮就放低要求抢庄，反别人的主要更有把握，自己亮过的花色有更多张就加固。阈值放在 `smartTuning` 里，模拟器用 `--tune declareSingle=9` 之类调参。
- **扣底**：优先扣副牌里的短门、无分小牌，保留对子、A 和主牌。
- **庄家计划（扣底 + 叫朋友一起定）**：挑最短的一门副牌叫 A，缺门最好、其次单张；自己有几张 A 就叫第几加一张；扣底时把这门垫到只剩自己的 A 加每个叫法一张最小的引牌，其余全垫掉。两个朋友尽量叫两门：能垫出第二门就两门各叫一张，不能就第二个朋友按普通叫法挑另一门，不再同一门叫第一、二张，因为两张 A 常落在同一人手里，只找到一个朋友。为垫门而埋分牌或 K 得不偿失时不做计划，退回普通扣底和叫法。开局时留下的引牌优先打出去找朋友。加强版把「普通扣底」也放进候选交给推演决定。A/B 里定位到早先的代价几乎全来自同门叫两张，改掉后计划叫法与旧叫法的庄家守住率持平（43%），垫门本身影响在噪声内。
- **首出（lead）**：先出压不住的牌型，有分更好，都压不住时甩牌；庄家阵营主牌多时拉主；庄家先找朋友：开局前几墩、自己主牌够硬时，用朋友牌花色里的无分小单张引牌，叫的是「第一张 A」时这一墩由朋友的 A 收走，顺带亮明身份；握着朋友牌的跟牌方也会主动用朋友牌收墩来亮身份，越早越值；对手已断门的花色不再送，队友断门的花色喂他毙；最后几墩能赢就赢。
- **跟牌（follow）**：用最小、最大、送分、毙牌四种确定策略加二十个随机样本生成候选，按「这墩分归我方还是对方」加用牌成本打分。主牌首出时用记牌判断当前赢家是否已经稳了，不稳的墩上送分打折；末墩额外加权，闲家为了抠底、庄家为了保底都要抢。阵营判断：庄家和已现身的朋友互为队友；手里握着朋友牌的人把自己当庄家一方；闲家只有在朋友全部现身后才把其余人当队友。

A/B 结果（`pnpm sim -- --smart ab`，偶数座位新版、奇数座位旧版）：

| 对局 | 每轮升级 新版 / 旧版 | 整局获胜 新版 / 旧版 |
|---|---|---|
| 6 人 500 局 | 0.435 / 0.417 | 784 / 659 |
| 5 人 500 局 | 0.258 / 0.252 | 636 / 363（3 席对 2 席） |
| 6 人对随机机器人 300 局 | 0.891 / 0.421 | 668 / 168 |

单项来看跟牌的稳墩判断贡献最大，首出的断门判断次之，亮主和叫朋友的改动对胜率影响在噪声范围内，但叫法更符合真人习惯。

### 3.6.1 搜索机器人（第三版）

`packages/engine/src/searchbot.ts`，确定化蒙特卡洛：

- **补全手牌**：别人的手牌未知，但已知约束不少：谁在哪个花色断门、每张牌还剩几张、亮出的牌还在谁手里、庄家知道底牌。按这些约束把剩余的牌随机分给其他人和底牌，按剩余容量加权，冲突时重试，实在不行退回忽略断门。
- **推演**：对每个候选出法（取二版规则打分的前 8 到 10 个），在同一份采样上用二版机器人把这局打完，收益按我方视角算：闲家分相对下庄线的偏移，加上升级数的一半。同一采样、同一推演随机序列用于全部候选，降低方差。
- **预算**：带时间预算，到点就停，至少两次采样。本机一次推演约 7 毫秒，600 毫秒预算大约 20 次采样。服务端用异步版本，每次采样之间让出事件循环，不会卡住收发消息；局面若在搜索期间变化（重发、结束、有人接管），结果作废。
- **逐轮淘汰**：采样到 4、8、14 次时分别只保留均值前 5、3、2 名的候选，剩余预算全给它们，同样的时间里最终选择更准。
- **底牌采样偏好**：非庄家视角下，补全底牌时按「庄家会不会扣这张」加权：主牌几乎不扣，分牌很少扣，副牌小牌最常扣。
- **残局精确求解**（`endgame.ts`）：每人剩 3 张以内时，在确定化局面上做双方阵营的极小极大搜索代替启发式推演，穷举全部合法出法，带节点预算；末墩抠底这类关键节点算得准。本机一份残局全部出法几毫秒。
- **庄家决策**：扣底比较第二版首选加末位换牌的几组变体，叫朋友比较打分前几的几组叫法，都用同样的采样推演选最好的，预算是出牌的两倍。
- **并行采样**（`apps/server/src/searchPool.ts`）：服务端起一个 worker 线程池（默认核数减一，可用 `SEARCH_WORKERS` 覆盖），主线程生成候选、逐轮淘汰、选优，worker 只做「给一批种子跑采样」的纯计算。每轮给每个 worker 派两个种子，合并后淘汰再派下一轮，直到预算用完；worker 起不来自动退回单线程。线上机器配 shared-cpu-4x 1GB，三个 worker 并行。
- **接入**：房主在大厅选「普通」或「加强」机器人，默认加强，出牌每手 1.1 秒预算，加强模式下固定等待缩短到 0.1 秒。亮主仍用二版。
- **效果**：本机 12 局 6 人 A/B，搜索版只给极小预算（每手 60 毫秒、最多 8 次采样、6 个候选）对二版：一期 0.444 对 0.405，二期 0.466 对 0.382，每轮升级约高 22%。线上最小机器 0.9 秒预算实测每手 9 到 14 次采样、5 到 8 个候选。

#### 四人对家模式的专门强化

四人模式阵营从第一墩就公开，搜索里最不可靠的「猜朋友」没有了，可以把力气花在别处。三处专门处理，都只在 `players === 4` 时生效：

- **残局提前算准**：精确求解门槛从每人 3 张放宽到 5 张，节点预算 6 万。为此求解器加了三样只影响速度的东西：跟牌出法按牌的身份去重（两副牌同身份的牌出哪张都一样，分支少一大半）、走子排序（先看能赢的和垫分少的，剪枝更多）、置换表（同样的剩余手牌、当前墩与得分只算一次，只存窗口内算准的值）。实测四人局每人 5 张时 6 万节点内约八成能算完，平均 70 毫秒；6 张只有四成能算完，不划算，所以停在 5。五六人维持 3 张（放宽到 4 张的对照按要求中止，未验证的不改）。
- **采样先验**：补全别人的手牌时，主牌按公开信息加权：庄家扣底会留主（权重 3.0），亮主的人主多（1.6），主动领过主的人主多（2.5）。权重只改变分布，不排除任何可能。用真实暗牌校验：各家主牌数的平均误差从 1.01 张降到 0.85 张，其中「领过主」这条信号最有用。
- **参数按模式放宽**：服务端按时间预算搜索时，四人的采样上限乘 1.5、候选至少 12 个（`tuneForMode`）；模拟器按固定采样数对比时不放宽，保证公平。

二版规则也加了一组四人专用打法（`partner` 特性）：主牌计数拉主（自己的主比外面平均每人多 15% 就拉，闲家也拉）、闲家残局前留稳赢的对子和拖拉机到末墩抢底、庄家留最大的主到末墩保底、对手在赢而对家还没出时不垫分牌、第二家不用大牌硬抢没分的墩。这组规则在 320 局同种子的二版对二版对照里效果在噪声之内（每轮升级 0.305 对 0.310，对照组两边都关是 0.310 对 0.305），逐条关掉也一样，说明二版原有的打分已经覆盖了这些情形。保留它们是因为不亏，而且让推演里的残局打法更像人。

**效果**（本机四人 A/B，搜索队坐 0、2 号位对二版队坐 1、3 号位，每手固定 8 次采样、8 个候选，同一组种子各 120 局）：基线等价设置下搜索队每轮升级 0.355 对二版 0.329，高 8%，整局获胜 66 对 54；三步全开后 0.374 对 0.308，高 21%，整局获胜 77 对 43。四人搜索随采样数增强很快：24 次采样的 48 局对照 0.442 对 0.251，整局获胜 39 对 9，坐庄守住 54% 对 38%；线上每手 50 到 100 次采样。注意 24 局以下的对照分辨率只有约 ±0.04，看不出这种量级的差别，第一轮 24 局基线里搜索队甚至略落后（0.338 对 0.354），是噪声。

### 3.6.2 配合打法

阵营一旦明确（庄家与已现身的朋友互为队友；握着朋友牌的人把自己当庄家一方；闲家在朋友全部现身后把其余人当队友），机器人按下面这些真人配合的常识出牌：

- **队友稳赢就送分**。判断"稳"：主牌首出看外面有没有更大的主；副牌首出要本门外面没有更大的牌，且后面还没出牌的人没有一个已知断门，否则可能被毙。队友稳赢时优先把自己手里的 5、10、K 喂上去。
- **不抢队友的墩**。队友已经在赢，自己再用更大的牌盖过去没有意义，除非能把不稳的墩变稳。
- **喂队友毙**。队友已知在某门断门而对手没有断门时，主动出那门的牌让队友用主毙，带分的牌最好。
- **别给对手毙**。对手已知断门的花色不再出，尤其不出分牌。
- **庄家先找朋友**。开局用留下的引牌把朋友引出来；朋友都现身后主牌够多就拉主，把闲家的主消耗掉。
- **末墩齐心**。最后一墩闲家全员抢抠底，庄家阵营全员保底。

- **庄家首先找队友**。庄家只要手里还有为叫朋友留下的引牌，前十墩内轮到首出就直接领出，不看主牌强弱、不交给推演比较，把牌权送给握 A 的朋友；叫的是第二张或第三张时，先把自己手里的 A 出掉把序号往前推（有两张就一对一起出），再领引牌；朋友现身后知道庄家把那门垫绝了，会把那门传回来让庄家用主毙。门槛 `smartTuning.openingMinTrumps` 默认 0。
- **拖拉机早出**。连对拖拉机在前十墩内优先领出，免得被别人领一对拆散。
- **先短后长**。有多门稳赢的牌时先出短门的，防止被人趁机绝门。
- **领小主让队友接管**。阵营已明、自己没有稳赢的牌时，用小单主把上手权交给队友的大主。
- **见到做庄家队友的机会首选做队友**。只要有一手合法出法能用朋友牌收下这墩、或轮到首出时能领出朋友牌，让序号凑满成为庄家队友，就一定这么打，两版机器人都不交给推演比较；把朋友牌垫进别人赢的墩里不算机会。这两条是按真人打法定的硬规则；机器人互打 150 局里它们让庄家守住率从 38% 降到 27%（6 人），因为阵营一亮闲家立刻配合，数字记在这里供日后对照。
- **亮主的取舍**。首局无人亮主时见级牌就亮抢庄，之后抓到第二张再加固；无主通常对闲家有利，只有级牌是 10 或 K 时才更愿意亮无主，因为领一对王能逼出分牌。

以上五条来自网上升级、找朋友攻略的整理（见 README 参考资料），加入后 A/B 150 局：6 人每轮升级 0.447 对 0.413，5 人 0.257 对 0.244。

### 3.6.3 四人对家模式的人类固定打法

从网上的双升攻略里整理出的口诀，写成二版机器人的固定规则（`partner` 特性，只在四人对家模式生效；搜索版的候选排序和推演也用它）。每条后面是出处。

**庄家**

- 扣底一定要绝一门副牌，这是和对家过桥的通道；挑最短、没有 A 的一门整门扣掉。没分的副牌小对不必留，一对 Q 也扣。底里最多放 5 分。（91y 庄家打法下篇）
- 清主：四个以上主对，或三个主对带一对大王，上手就打主对，一连四对外面基本没主了；起了主对之后不打单张。三个主对没有大王对，先单吊两三轮再清主。（91y 上篇）
- 副牌留 A 加单张不打，A 留着进手、压制对手甩牌、跑对家的分。（91y 中篇）
- 有 AK 带一对的副牌，先出一张小牌问路；一对 10、一对 K 不乱冲。（91y 下篇）
- 上家出没分的单张或小对副牌，不用主去毙。（91y 下篇）
- 守庄方有连对：先出旁门 A 再出连对，免得旁门的分被人跑掉。（搜狐 80 分记忆推理技巧）

**庄家的对家**

- 先出庄家还有牌的门的 A，让庄家跑分；再出庄家已断门的 A。对家不该藏单 A。（搜狐）
- 出完大牌只剩小对时不冲小对，改为吊主或刺庄家的断门，把牌权还给庄家。（搜狐、边锋双升攻略）
- 庄家中途吊主是信号：对家停出副牌，跟着拉主。（搜狐）
- 除非要过桥，不主动捅庄家的断门。（拖拉机高手帮庄心得）

- 一般情况下庄家不先吊主：四人主牌平均每人 9 张，庄家阵营主牌达到 11 张以上才主动吊主，其余交给「自己的主比外面平均每人多 15%」的占优判断；清主条件成立时不受此限。无主除外：无主全桌只有 12 张主，4 张就可以吊，占优判断的最低张数也降为 3。模拟 300 局全二版对局，门槛从 7 改到 9 庄家守住率 43.3% → 44.3%，9 到 11 持平（44.2%），11 是按牌桌经验定的。

**通用**

- 某门副牌只剩一张，不管是不是分，主动打出去，免得以后被迫垫分。（搜狐）
- 无分的副牌有多对，赶快出，可能抓到对 10、对 K。（搜狐）
- 对手在某门断门而自己那门有对子，先出主对把他的主拉掉，副对才安全。（搜狐）
- 早中期不乱甩牌，对方有最后出牌权。（搜狐；引擎里甩牌只在稳赢时提出）

未采纳的：「从中间开始垫牌」这条各家说法互相矛盾；「首张冲副 10」是无奈之举；「控制倒数第 4、3 个主防双扣」由残局精确求解代替。

出处：[91y 庄家打法技巧（上）](https://m.91y.com/news/wanfadaquan/doudizhuwanfa/2016/0415/1643.html)、[（中）](https://m.91y.com/news/wanfadaquan/doudizhuwanfa/2016/0415/1644.html)、[（下）](https://m.91y.com/news/xinde/1645.html)、[搜狐：玩 80 分双升需要学会的记忆和推理技巧](https://m.sohu.com/n/448262530/)、[边锋：双升游戏经验攻略](https://www.gameabc.com/news/201704/3407.html)、[pagat：Tractor](https://www.pagat.com/kt5/tractor.html)。

**效果**：同种子 320 局二版对二版（开这组规则 vs 不开）：0.332 对 0.322，整局获胜 169 对 151；之前没有这组人类规则、只有第一批四人规则时是 0.305 对 0.310。绝门做成强制（整门加 45 分）反而略差（0.326 对 0.329），所以保留为软偏好（加 20 分）。这些差别都在 ±0.01 的噪声边缘，结论是这组规则不亏、略有帮助，主要价值是让机器人打得像人。

### 3.6.4 手牌推断网络

搜索补全别人的手牌时，原来按各家剩余张数均匀分配（四人另有手写的主牌先验）。推断网络根据公开信息预测每张没见过的牌在谁手里、或在底牌里，补全时按它的概率加权。四五六人各一个模型。

- **输入**：从「我」的视角编码，座位用相对位置。牌的身份规范化：主花色固定排在第一个花色槽，另加级别独热编码，这样不同主花色、不同级别的局面能共用学到的规律。特征包括我的手牌、没见过的牌、每个人打出过的每张牌、每人每组的断门和领出次数、手牌数、得分、庄家与亮主者、已知阵营、叫朋友的牌和进度、本墩首家与首出组，四人 466 维、五人 540 维、六人 614 维。
- **输出**：每个（身份, 位置）一个分数，在位置维度上按掩码做 softmax。掩码排除没有空位的位置和已知断门的人。损失是每张没见过的牌的交叉熵。
- **网络**：两层 512 维的全连接层，权重 2.5 到 3 MB，放在 `packages/engine/models`。训练用 PyTorch（`ml/train_belief.py`，本机 M1 Pro 每个模型 20 秒左右）；推理在引擎里用纯 TypeScript 实现，不依赖运行库，每步只算一次，约 1 毫秒。
- **采样接入**：每张牌分给某个位置的权重 = 剩余容量 × 网络概率 ÷ 初始容量；网络给出均匀概率时正好退化为原来的按容量分配。断门、张数这些硬约束仍由采样器保证。有网络时不再用手写先验和底牌偏好。`BELIEF=0` 环境变量或 `--tune belief=0` 可以关掉。
- **训练数据**：二版机器人自对弈，出牌时有 15% 的概率改从规则打分前四名里随机挑，增加多样性；在出牌决策点按 25% 抽样，从出牌人视角记录。四人约 62 万、五人 45 万、六人 50 万个样本，独立种子的测试集各约两万个（`packages/engine/src/sim/beliefData.ts`）。
- **离线效果**（`sim/beliefEval.ts`，每人数 800 个新局面、每局面 24 次补全，看每个对手每组牌张数的估计误差）：

| 人数 | 测试交叉熵比均匀分配低 | 对手各组张数误差 | 底牌各组张数误差 |
|---|---|---|---|
| 4 人 | 14.6% | 12.34 → 10.90，降 11.7% | 3.02 → 2.14 |
| 5 人 | 7.9% | 18.54 → 17.25，降 6.9% | 3.38 → 2.47 |
| 6 人 | 6.3% | 22.67 → 21.44，降 5.4% | 3.40 → 2.41 |

四人的「原来」已包含手写主牌先验。四人提升最大，因为阵营从开局就公开、两副牌每种牌只有两张。把网络加大到三层 1024 维只多降 0.3 个百分点，模型大四倍，没有采用。

- **注意**：训练数据来自机器人自对弈，网络学到的是「机器人会怎么出牌」。真人的出牌习惯不同，对真人的推断效果可能打折扣；以后有足够的真人对局回放可以拿来微调。

**对局效果**（四人，`--smart beliefab`：四个座位都是搜索版，偶数座位开推断网络、奇数座位关，每手 8 次采样、8 个候选，80 局游戏 2156 轮）：开网络的一方每轮升级 0.430，关的一方 0.369，高 16.5%；整局获胜 47 局对 33 局，坐庄守住 55% 对 51%。8 个进程各自的差值有 6 个为正，均值 +0.064，标准误 0.024，约 2.7 个标准误。

线上只对四人启用（服务端默认 `BELIEF_PLAYERS=4`）。五六人的模型也训练好了、离线误差也更低，但还没做对打验证，先不启用；要启用时设 `BELIEF_PLAYERS=4,5,6`。

### 3.6.5 完美信息价值网络

搜索补全别人的手牌后，局面就完全公开了。原来要用二版机器人把整局打完才知道结果，每次约 7 毫秒，还带着二版打法的偏差。现在推演只把当前这一墩打完，在下一墩开始时交给价值网络估这一局的最终收益。思路来自斗地主的 PerfectDou：训练时让网络看到所有人的牌，价值好学得多。只用于四人对家模式，因为五六人的阵营在补全的局面里仍不确定。

- **输入**：完全公开的局面，以庄家为基准排座位。各家手牌、底牌、已出的牌（规范化身份同手牌推断网络），每人得分、罚分、是否庄家方，本墩首家，已出墩数，无主，级别。355 维。
- **输出**：闲家方的收益，单位与搜索的收益一致：（闲家得分 − 2L）/ L + 升级数 × 0.5，庄家守住时升级数记负；庄家方取相反数。
- **训练**：二版机器人自对弈 8.8 万轮（10% 概率从规则前四名里随机挑），每墩开始时记录局面，这一局结束后用真实结局打标签，共 150 万个样本。训练时随机互换三个副牌花色槽做数据增强。两层 128 维全连接，0.2 MB，本机训练 30 秒。测试集上解释了结局方差的 65%，与真实结局的相关系数 0.81；三层 512 维的网络准确度一样，但推理慢十倍，没有采用。
- **截断规则**：推演打完当前一墩后，在下一墩开始时截断；每人只剩 4 张以内时不截断，推演到底；每人 5 张以内仍由残局精确求解接管。
- **速度**：同样 300 毫秒，每手采样从 45 次升到 639 次，约 14 倍。服务端四人局的采样上限随之放到 2000，worker 每轮领取的种子数按耗时自动加倍；本机 9 个 worker 每手 0.2 到 0.55 秒就采满 2000 次。

**对局效果**（四人，`--smart valueab`：四个座位都是搜索版，偶数座位开价值网络、奇数座位关，每手同样 300 毫秒，48 局游戏 1280 轮）：开网络的一方每轮升级 0.459，关的一方 0.353，高 30%；整局获胜 34 局对 14 局；坐庄守住 55% 对 48%。8 个进程里 7 个为正、1 个持平，均值差 +0.108，标准误 0.024，约 4.5 个标准误。线上默认对四人启用（`VALUE_PLAYERS=4`，`VALUE=0` 关闭）。

### 3.7 回放

服务端为每一局记录发牌前的完整状态和之后的全部操作，保留最近六局并随房间快照落盘。客户端请求某一局的回放后，用共享的引擎从初始状态重放操作，按墩列出每个人的出牌、赢家、分数、朋友现身和甩牌失败，并可展开各人起手牌与底牌。因为引擎是确定性的，回放数据只有操作序列，体积很小。

## 4. 部署

- Fly.io，区域 ewr，一台 shared-cpu-4x 1GB 机器（搜索机器人多线程采样用得上多核），空闲自动休眠、有访问自动唤醒，按秒计费。
- Docker 多阶段构建：先 `pnpm build` 出引擎、协议、前端静态文件和服务端，运行镜像只含服务端产物和 `apps/web/dist`。
- Fastify 同时托管静态文件和 `/ws`，`/healthz` 给 Fly 健康检查。
- 自定义域名走 `fly certs`，HTTPS 是 PWA 和微信内置浏览器的硬要求。
- 1GB 卷挂在 `/data` 存房间快照。
- 环境变量只有 `PORT` 和 `SNAPSHOT_DIR`，没有秘密。

## 5. 测试

- 引擎单元测试（vitest）：牌力比较、拖拉机识别、跟牌约束、赢墩判定、结算阶梯，全部表驱动。
- 属性测试（fast-check）：随机合法对局必然终止；每局分牌总和恒为 300；`viewFor` 永不泄露他人手牌。
- 命令行模拟器 `pnpm sim --players 6 --games 1000`，随机机器人跑完整局，用来抓引擎崩溃和死锁。
- 服务端集成测试：多个 ws 客户端跑完一局，中途断线重连一次。
- Playwright 冒烟：手机视口下创建房间、加入、打完一墩。

## 7. 规则确认记录

2026-09-10 确认的八条，已写入上文并作为引擎默认值：

1. 亮主只看张数，三张 > 两张 > 一张。
2. 三条与相邻对子不构成拖拉机。
3. 5 人 60 分一级、120 分下庄；6 人 50 分一级、100 分下庄。
4. 庄家自己打出的朋友牌也计入序号。
5. 打 A 守住即获胜。等级顺序 5, 10, K, 2, 3, 4, 6, 7, 8, 9, J, Q, A。
6. 甩牌失败每张罚 10 分。
7. 首局无人亮主重发。
8. 抠底固定单张 ×2、对子 ×4、拖拉机 ×8。
9. 三条不必拆成对子去跟对子（2026-09-10 试玩后补充）。
10. 首局谁最终抢到主谁坐庄，被反主则庄家随之改变（2026-09-10 试玩后补充）。
11. 三张王不论大小混不混都可以亮或反（2026-09-10 试玩后补充）。
12. 四人对家模式：两副牌、每人 25 张、底牌 8 张、40 分一级、80 分下庄（2026-09-11 确认）。等级顺序原定与找朋友相同，2026-10-15 改为第 15 条。
13. 闲家得 0 分（大光）时庄家阵营升 3 级，其余阶梯不变；各人数模式都适用（2026-09-14 试玩后报告的 bug，按通行规则修正）。
14. 自己亮了主、别人还没反时，只能用更多张同样的牌加固，不能改亮别的花色，也不能改亮王；被别人反了之后可以按正常规则再反（2026-10-15 试玩后报告的 bug）。线上存档的回放里有两次机器人自己换了花色：一次把 ♠3♠3 换成一对小王，一次把 ♥6 换成 ♦6♦6，后者会让人以为方块压红桃是比较大小出了错。
15. 四人升级的等级：从 2 开始、A 结束；升级时第一次到 5、10、K 不能跳过（打 4 升两级只能到 5）；在 A 上坐庄守住才赢下整局。找朋友的等级阶梯不变（2026-10-15 确认）。服务器上进行中的四人局在更新后按点数换算到新阶梯，显示的级别不变。
16. 五人找朋友：庄家阵营守住就由原庄家连庄，不再交给朋友；下庄仍由庄家逆时针方向第一个闲家接庄。六人局和四人局不变（2026-10-17，GitHub issue #1）。

仍有三处是我对上述规则的解读，写进了引擎配置项，实际打起来不对再改：

- 同张数不能反主，即两张大王不能反两张级牌。这是「只和张数有关」的字面理解。
- 甩牌罚分按甩牌总张数计，而不是按被迫打出的最小组件计。闲家被罚从闲家得分中扣，最低到 0。
- 抠底时最后一墩是三条，倍数按 ×8。
